SimFlow Documentation

v1.1.4 · UE 5.6

A modular, data-driven task and flow framework for VR simulations, tutorials and procedural gameplay. Author procedures as node graphs; run them from a component; drive your UI from what they report.

    What SimFlow is

    SimFlow runs procedures — an ordered set of things a person has to do, with rules about what happens when they do them wrong, out of order, or not at all.

    You author a procedure as a node graph asset. A component on an actor runs it. Your existing Blueprints feed it events and listen to what it reports.

    Good fit

    • The player must complete steps, and you need to know whether they did
    • Steps have pass/fail conditions, timeouts or scoring
    • The same procedure appears in several scenarios and should be authored once
    • A session might be interrupted and need to resume
    • An instructor needs to skip, retry or fail a step on the trainee's behalf

    Not a fit

    • Cutscenes and camera work — use Sequencer
    • Enemy decision-making — use Behavior Trees
    • Simple one-off triggers — a Level Blueprint is less machinery

    Installing and enabling

    1. Copy the SimFlow folder into YourProject/Plugins/SimFlow.
    2. Right-click the .uproject → Generate Visual Studio project files (or run GenerateProjectFiles).
    3. Build the editor target. SimFlow is a C++ plugin, so the project needs at least one C++ module — if yours is Blueprint-only, add any empty C++ class once from the editor and Unreal converts it.
    4. Enable SimFlow in Edit → Plugins if it is not already on, and restart.
    Two modules

    SimFlowRuntime ships in packaged builds. SimFlowEditor (the graph editor) is stripped on cook. Only node data is packaged, never the visual graph.

    Targets UE 5.6. It also builds on 5.4/5.5 — see Engine compatibility in the developer guide for the one line that may need adjusting.

    Core concepts

    Flow assetThe graph you author (asset type SimFlow Graph). A template, never modified at runtime, so one asset can drive several actors.
    Flow instanceA running copy. Duplicates every node, so each run owns its timers, retry counts and loop counters.
    NodeA box in the graph. Execution arrives at an input pin, the node acts, then pushes out through an output pin.
    TaskThe unit of work inside a Task node. Where the player actually does something. Blueprint-subclassable.
    ConditionA yes/no question about the run. Used by Branch nodes and waiting tasks.
    BlackboardKey/value store for the run: score, mistakes, answers, your own state.
    EventA gameplay tag raised from anywhere. How the world tells the flow something happened.

    Creating your first flow

    Content Browser → right-click → SimFlow → SimFlow Graph. The new asset opens with a Start node already placed.

    1. Right-click empty graph space → Tasks → Task
    2. Drag from Start.Out onto the Task node's In pin
    3. Select the Task node and set Task to one of the built-ins
    4. Expand the Task row — the arrow beside the dropdown — to reach the task's own settings
    5. Right-click → Flow Control → Complete Flow, wire Task.Completed into it
    6. Save

    To run it: add a SimFlow Component to any actor, set Flow Asset, set Start Mode to Auto - On Begin Play, press Play, and type SimFlow.Debug 1 in the console.

    Or skip authoring entirely: Tools → SimFlow → Create Sample VR Tutorial Flow (console: SimFlow.CreateSample) builds a complete example that exercises every feature and opens it.

    The Details panel splits in two

    Time Limit and Auto Retry belong to the node. Display Name, Instruction and Score belong to the task nested inside it. The node owns how the flow treats this step; the task owns what the step is.

    Node reference

    A node is the box in the graph. It is woken through one of its input pins, does its job, then pushes execution out of one output pin and goes back to sleep — whatever is wired to that output wakes next. A few nodes deliberately stay awake after firing (Parallel, Loop, a racing Join), which is how more than one part of the graph runs at the same time.

    Every node, whatever its type, also carries a Node Comment drawn on the node in the graph, and every node is duplicated per running flow — so two trainees running the same asset never share node state.

    NodeCategoryIts one job
    StartFlow ControlWhere a run begins. Several per graph, each named
    TaskTasksRun one step and route on how it ended
    DelayFlow ControlWait, then carry on
    BranchFlow ControlTake one road out of several, by condition
    Random BranchFlow ControlTake one road at random, optionally weighted
    ParallelFlow ControlTake every road at once
    JoinFlow ControlBring those roads back together, or race them
    LoopFlow ControlRepeat a section
    Sub FlowCompositionRun another flow asset as a child
    CheckpointPersistenceName a point in the run, optionally save there
    Set Blackboard ValueDataWrite a key inline, without a task
    FinishFlow ControlEnd the whole run with a verdict

    Each entry below gives the pins, the properties and a worked example. In the sketches, an indented name is the output pin execution leaves through, and ▶ points at what it is wired to.

    Start Flow Control

    Where execution begins. It has no input pin — nothing in the graph can jump back to a Start node, which is why re-entering a section means looping, not restarting.

    A graph may hold several Starts with different names. Start Flow uses whichever entry the component's Entry Name property names (Default out of the box); Start Flow From Entry overrides it per call. That is how a single asset serves a full scenario, a practice run and an assessment run without duplicating the content — each entry sets up differently and then dives into the same shared body.

    Out
    PropertyDefaultMeaning
    Entry NameDefaultPass this to Start Flow From Entry to begin here
    One asset, three ways in

    The scenario body lives in a Sub Flow. Each entry decides what the trainee gets before it.

    [Start  "Default"]
    Out ▶ [Task  Safety briefing] ▶ [Sub Flow  Valve_Procedure]

[Start  "Practice"]
    Out ▶ [Set Blackboard  bShowHints = true] ▶ [Sub Flow  Valve_Procedure]

[Start  "Assessment"]
    Out ▶ [Set Blackboard  bShowHints = false]
        ▶ [Checkpoint  Assessment begins] ▶ [Sub Flow  Valve_Procedure]

    From Blueprint: Start Flow From Entry ("Practice") on the SimFlow Component. The hint tasks inside the shared body sit behind a Branch on bShowHints.

    Task Tasks

    Runs one task and routes on how it ended. This is the node you will place most, and the only one that shows up as a step to the trainee.

    The split is worth holding on to: the node owns how the flow treats this step — the time limit, the retries, the early-out — and the task nested inside it owns what the step actually is. Swap the task and the routing survives.

    InCompletedFailedSkippedTimedOut
    PropertyDefaultMeaning
    TasknoneA built-in or your own Blueprint task
    Time Limit0Seconds before leaving via TimedOut. 0 = no limit
    Auto Retry on FailureoffRestart automatically when the task fails
    Auto Retry Limit1How many automatic restarts
    Auto Retry on TimeoutoffAlso auto-retry on timeout
    Fallback to CompletedonUnwired Failed/Skipped/TimedOut fall through to Completed
    Abort ConditionnoneChecked every frame; when it passes the task ends early
    Abort ResultFailedWhich pin an aborted task leaves through

    Each frame the node ticks the task, then evaluates the Abort Condition, then checks the time limit. When the task reports a result the node considers an auto retry first, and only leaves through a pin if it is not retrying — so a retried task never fires the Failed branch. Auto retry also respects the task's own Allow Retry box, so a task marked one-shot stays one-shot.

    Fallback to Completed is what keeps linear flows tidy — wire only Completed and the rest falls through. It only redirects pins with no link at all. Turn it off when a failure must genuinely stop the flow.

    A Task node with no task passes straight through

    It fires Completed immediately and logs a warning to LogSimFlow. A scenario that races to the end is usually a row of empty Task nodes.

    A step that can time out into a hint

    Forty-five seconds to find and put on the gloves. A failure retries itself twice before the flow ever sees it; a timeout sends the trainee round again through a hint.

    [Task  Don the gloves]
    Task                   Wait For Event  (Sim.Equip.Gloves)
    Time Limit             45 s
    Auto Retry on Failure  ✓  limit 2

        Completed ▶ [Checkpoint  Geared up]
        TimedOut  ▶ [Task  Log "The gloves are on the shelf by the door"]
                          Completed ▶ back into [Task  Don the gloves] . In
        Failed    ▶ (unwired — falls through to Completed)

    Wiring a TimedOut hint back into the same node's In is the standard nudge loop. Bound it with the task's Max Retries or with a Loop node around the pair, or a trainee who never finds the gloves never leaves.

    Delay Flow Control

    Waits, then continues. The graph's beat — a pause between two lines of voice-over, a moment for an animation to land, a settling time before you test a gauge.

    It counts flow time, not wall time: a paused flow does not tick, so a 10 second Delay is 10 seconds of the trainee actually running. A Duration of 0 passes through on the same frame.

    InOut
    PropertyDefaultMeaning
    Duration1.0Seconds to wait. Respects pause
    Delay node or Delay task?

    The node is invisible scheduling — it is not a step, so it never appears in the UI or counts toward progress. The task is a step the trainee is waiting through, so it shows up, can be skipped, and offers a random extra. Use the node for timing, the task for "hold for 30 seconds while it depressurises".

    Letting a cutscene breathe 
    [Task  Play alarm VO]
    Completed ▶ [Delay  2.0 s] ▶ [Task  Play supervisor VO]
                                       Completed ▶ [Delay  0.5 s]
                                                 ▶ [Task  Evacuate the area]

    Branch Flow Control

    The graph's if / else-if / else. Cases evaluate top to bottom and the first that passes wins; if none do, execution leaves through Default. Pin labels fall back to the condition's own description, so a well-configured condition labels its pin for free.

    InCase 0Case 1Default
    PropertyDefaultMeaning
    Cases2 emptyOrdered list; each has a Label and a Condition
    Fire All Matching CasesoffFire every passing case, giving a conditional fan-out
    Has Default PinonShow a Default pin for when nothing matched

    With Fire All Matching Cases on, the Branch becomes a Parallel with entry requirements: every passing case fires at once. The number of live branches then varies at runtime, so do not converge them on a Wait For All Join — it waits for a fixed count that may never arrive.

    Turn Has Default Pin off and a Branch that matches nothing simply ends that thread of execution. That is a deliberate dead end, and a useful one at the tail of a fan-out.

    An empty case is a dead pin, not a "true"

    A case with no condition never passes. If your Branch always takes Default, check that every case actually has a condition object assigned.

    Grading at the end of a scenario 
    [Branch  3 cases]
    Case 0  "Distinction"  Score Threshold  ≥ 90
        ▶ [Task  Log "Distinction"] ▶ [Complete Flow]

    Case 1  "Pass"         Score Threshold  ≥ 60
        ▶ [Task  Log "Pass"] ▶ [Complete Flow]

    Default
        ▶ [Sub Flow  Remediation_Debrief] ▶ [Fail Flow]

    Order is the whole trick. Put ≥ 60 first and it swallows every distinction, because the first match wins.

    Random Branch Flow Control

    Picks one output at random. This is how a scenario stops being memorisable — run it three times and the fault is different each time, so the trainee has to diagnose rather than recall.

    Weights are optional and positional: a missing entry counts as 1, and a weight of 0 is never picked. If every weight resolves to zero it falls back to an even pick rather than stalling. Avoid Repeats zeroes out whatever came up last, so back-to-back passes through the node — loop iterations, for instance — always differ. That memory lasts for the run and resets when the flow restarts.

    InOut 0Out 1…
    PropertyDefaultMeaning
    Num Outputs22–16 output pins
    WeightsemptyOptional per-output weight; missing entries count as 1
    Avoid RepeatsoffNever pick the same output twice in a row

    Resolves on the server only, so all clients agree.

    Three drills, three different faults

    The common fault comes up twice as often as the exotic ones, and no trainee gets the same fault twice running.

    [Loop  Iterations 3]
    Loop Body ▶ [Random Branch  3 outputs
                                  weights 2 / 1 / 1
                                  Avoid Repeats ✓]
                      Out 0 ▶ [Sub Flow  Fault_StuckValve]  ─┐
                      Out 1 ▶ [Sub Flow  Fault_LeakingSeal] ─┤
                      Out 2 ▶ [Sub Flow  Fault_BadGauge]    ─┘
                                                            ▶ [Loop] . Continue
    Completed ▶ [Branch  graded?]

    Parallel Flow Control

    Fires every wired output in the same frame, and each becomes an independent live branch with its own active nodes, all ticking together. Unwired pins cost nothing, so leaving Num Outputs at 4 and using two is fine. If nothing at all is wired, the node just ends that thread of execution.

    The branches share one blackboard. Two branches writing the same key is a race, and it is yours to arrange — give each branch its own keys unless you mean them to collide.

    InOut 0Out 1…
    PropertyDefaultMeaning
    Num Outputs22–16 branches, all fired at once. Unwired outputs are skipped
    Two hands, one procedure

    The trainee has to keep the gauge in view while turning the valve. Either order is fine; both must happen.

    [Parallel  2 branches]
    Out 0 ▶ [Task  Turn the isolation valve] ▶ [Join] . In 0
    Out 1 ▶ [Task  Keep the gauge in view]   ▶ [Join] . In 1

[Join  Wait For All]
    Out ▶ [Task  Report the reading]

    Without a Join the two branches just run to their own ends — acceptable if each finishes in its own Finish node, but the first one reached with Stop Other Branches on will kill the other mid-task.

    Join Flow Control

    Brings parallel branches back together. Wait For All converges; Wait For Any races.

    Wait For All counts distinct input pins, not arrivals — two hits on In 0 still count as one. Give every branch its own pin. When the last one lands the node fires and deactivates, which resets the count, and that is exactly what makes a Join safe to sit inside a Loop.

    Wait For Any fires on the first arrival and then stays alive on purpose, so the losing branch's arrival is swallowed and the section downstream can never run twice.

    In 0In 1…Out
    PropertyDefaultMeaning
    Num Inputs22–16 input pins
    ModeWait For AllWait For All converges; Wait For Any races
    Wait For Any leaves the loser running

    The Join stays alive to swallow the late arrival so downstream cannot fire twice — but the losing branch's task keeps running until the flow ends. For a timeout on a single task, the Task node's own Time Limit is better.

    Putting a clock on a whole section

    Two minutes to complete the shutdown. The Join does not report which arm won, so the work arm raises a flag before it arrives and a Branch reads it afterwards.

    [Parallel  2 branches]
    Out 0 ▶ [Sub Flow  Shutdown_Procedure]
              Completed ▶ [Set Blackboard  bInTime = true] ▶ [Join] . In 0
    Out 1 ▶ [Delay  120 s] ▶ [Join] . In 1

[Join  Wait For Any]
    Out ▶ [Branch]
              Case 0  "In time"  Blackboard Compare  bInTime == true
                  ▶ [Complete Flow]
              Default
                  ▶ [Fail Flow]

    Loop Flow Control

    Repeats a section. Its two inputs do different jobs: In starts a fresh loop and resets the counter to zero, Continue advances it by one. Wire the tail of the body back into Continue — forget that and the body runs exactly once and the graph stalls.

    Each pass it checks, in order: the Max Iterations safety valve, then the iteration count, then the Break Condition; then it writes the current 0-based iteration to the blackboard key if you gave one, and finally fires Loop Body. Because the break is checked before each pass including the first, a condition that is already true means the body never runs at all.

    Set Iterations to 0 to mean "until the break condition passes". With 0 and no break condition you are relying on Max Iterations, and you get a warning in LogSimFlow when it trips.

    InContinueLoop BodyCompleted
    PropertyDefaultMeaning
    Iterations3Number of passes. 0 = until the break condition passes
    Break ConditionnoneChecked before each pass; passing exits via Completed
    Max Iterations1000Safety valve so a bad loop cannot hang the game
    Iteration Blackboard KeynoneWrites the current 0-based iteration here
    Three practice reps, with an early exit

    Up to three attempts, but a clean run ends it early. The iteration is written to Rep so a task's instruction text can say which attempt this is.

    [Loop  Iterations 3
       Iteration Blackboard Key  "Rep"
       Break Condition  Blackboard Compare  CleanRun == true]

    Loop Body ▶ [Task  Perform the isolation check]
                    Completed ▶ [Set Blackboard  CleanRun = true]
                                ▶ [Loop] . Continue
                    Failed    ▶ [Task  Show the hint]
                                ▶ [Loop] . Continue

    Completed ▶ [Branch  did they get a clean run?]

    Both result pins route back into Continue, so a failed rep still counts as a rep. Route only Failed back and you get "retry until correct" instead.

    Sub Flow Composition

    Runs another flow asset as a child. This is what makes procedures reusable — build "put on the PPE" once, drop it into every scenario, fix it in one place.

    The node owns the child completely: it ticks it, pauses and resumes with it, and stops it if the parent stops. Sub Flows may nest, and each level is a real instance, so the debug HUD shows both.

    The two blackboard boxes decide how much the child sees. Both on and parent and child share state. Both off and the child is a sealed box — the right choice for a reusable procedure whose scratch keys should not leak into every scenario that uses it.

    InCompletedFailed
    PropertyDefaultMeaning
    Sub FlownoneThe flow asset to run
    Entry NameDefaultWhich Start node of the child to use
    Inherit BlackboardonCopy the parent's blackboard into the child at start
    Write Back BlackboardonCopy the child's back when it ends

    The child's final state picks the pin: Completed for a completed child, Failed for a failed or aborted one. An unwired Failed falls through to Completed, the same as on a Task node. Skipping the node from the UI stops the child and leaves via Completed.

    A PPE procedure used by every scenario

    PPE_Donning is its own asset with its own Start, its own tasks, and its own Complete and Fail nodes. Every scenario opens with it.

    [Start]
    Out ▶ [Sub Flow  PPE_Donning]
              Entry Name          "Default"
              Inherit Blackboard  ✓   (child can read bShowHints)
              Write Back          ✓   (Score and Mistakes come home)

                  Completed ▶ [Checkpoint  Geared up]
                              ▶ [Sub Flow  Valve_Procedure]
                  Failed    ▶ [Task  Log "Fix your PPE and try again"]
                              ▶ back into [Sub Flow  PPE_Donning] . In

    Checkpoint Persistence

    Does two things and then gets out of the way. It announces that a named point in the run has been reached — the instance broadcasts it, so your UI can say "Section 2 of 4" or an analytics hook can log the time — and it can optionally write a save right there.

    It passes through the same frame and costs essentially nothing, so be liberal with them: at each phase boundary, and after anything expensive to redo.

    InOut
    PropertyDefaultMeaning
    Checkpoint IdnoneYour name for this point
    Auto SaveoffWrite a save the moment this node is reached
    Save Slot NameemptyBlank uses the component's default slot
    Save User Index0SaveGame user index
    Saving is server-only

    In multiplayer an Auto Save on a client does nothing. Put the checkpoint wherever you like; the write happens on the authority.

    A long scenario that survives a crash 
    [Sub Flow  PPE_Donning]
    Completed ▶ [Checkpoint  "Phase1_Geared"   Auto Save ✓]
                ▶ [Sub Flow  Valve_Procedure]
                     Completed ▶ [Checkpoint  "Phase2_Isolated"  Auto Save ✓]
                                 ▶ [Sub Flow  Handover]

    A resumed session picks up at the last checkpoint written rather than at the start of a forty-minute run.

    Set Blackboard Value Data

    Writes a key inline, no task object needed. A pair of these plus a Branch is how most scenario state gets managed.

    Add accumulates onto the existing value instead of replacing it — the cheap way to count mistakes, points or attempts.

    InOut
    PropertyDefaultMeaning
    KeynoneWhich key to write
    ValuenoneBool, Int, Float, String, Name, Vector or Object
    AddoffAdd to the existing value instead of replacing
    Node or task?

    Use the node for bookkeeping the trainee should not see — it is not a step, so it never appears in the UI or in progress. Use the Set Blackboard Value task when the write genuinely is a step in the procedure.

    Counting mistakes and gating on them 
    [Task  Quiz  "Which valve isolates the line?"]
    Completed ▶ [Task  Quiz  Q2]
    Failed    ▶ [Set Blackboard  Mistakes += 1   (Add ✓)]
                ▶ [Task  Show the correct answer] ▶ [Task  Quiz  Q2]

    … later …

[Branch]
    Case 0  "Too many mistakes"  Blackboard Compare  Mistakes ≥ 3
        ▶ [Fail Flow]
    Default
        ▶ [Complete Flow]

    Finish Flow Control

    Ends the whole run with a verdict. It has an input pin and nothing else — nothing runs after it.

    The mode sets the run's final state, which is what On Flow Finished reports to Blueprint and what a parent Sub Flow node reads to choose between its Completed and Failed pins. Changing the mode retitles and recolours the node in the graph.

    In
    PropertyDefaultMeaning
    Finish ModeCompleteComplete / Fail / Abort. Changing it recolours and retitles the node
    Stop Other BranchesonKill anything still running in parallel
    Why the menu only lists one

    There is no separate "Fail Flow" entry to add — change Finish Mode on a placed node instead.

    A flow can also end without ever reaching one: when the last live branch runs out of wired outputs the instance completes on its own and logs that it hit a dead end. A Finish node is how you end a run deliberately, and the only way to end one as a failure.

    A pass / fail terminal 
    [Branch  graded?]
    Case 0  "Pass"  Score Threshold ≥ 60
        ▶ [Task  Log "Scenario complete"]
          ▶ [Complete Flow   Stop Other Branches ✓]
    Default
        ▶ [Task  Log "Scenario failed - see the debrief"]
          ▶ [Fail Flow       Stop Other Branches ✓]

    With Stop Other Branches on, a monitoring branch still watching a gauge somewhere in the graph is torn down cleanly instead of ticking on past the end of the run.

    Wait For Event

    Blocks until a gameplay tag is raised. The main way world interactions advance a flow.

    PropertyDefaultMeaning
    Event TagnoneThe tag to listen for
    Match Child TagsonListening for Sim.Grab also accepts Sim.Grab.Extinguisher
    Accept Already RaisedoffSucceed at once if the tag fired earlier this run
    Expected PayloademptyWhich object the event has to be about. Empty = any sender will do
    Mismatch PolicyCount MistakeWhat happens when the tag is right but the object is not

    Expected Payload is what lets ten buttons broadcast the same tag while only the intended one advances the flow. Each button sends itself as the payload and knows nothing about the exercise; the flow asset holds the answer. See Recognising objects.

    Bind On Payload Rejected for the buzzer or the hint — it passes the object and the match quality, so a near miss can get different feedback from a random prop.

    The most common setup mistake

    Leave Event Tag unset and the task succeeds instantly — there is nothing to wait for. A warning appears in the Output Log, and the score is still awarded, so it can look like the step worked.

    Accept Already Raised and payloads

    When Expected Payload is set, Accept Already Raised is ignored and a verbose line is logged. A past event kept only its tag, so there is no object left to check — honouring the flag would let the wrong one satisfy the task.

    A widget cannot be a payload

    self in a UMG graph is a UUserWidget — neither an Actor nor an Actor Component — so a query finds no actor behind it and always scores No Match. Broadcast from the owning actor instead. Since 1.1.3 the log names the offending class rather than leaving you with a task that never completes.

    Place Object In Zone 1.1.2

    “Put the foam extinguisher in the bay.” Watches a SimFlow Zone and judges what turns up in it. The zone reports what is there without an opinion; this task holds the opinion, so the same bay can be the right answer in one exercise and a distractor in the next without touching a Blueprint.

    PropertyDefaultMeaning
    ZoneemptyActor Query for the zone, usually a tag like Zone.PartsBin
    Accepted ItemsemptyWhat belongs there. Tags are the useful form, since they cover spawned copies
    Required Count1How many accepted items must be in the zone at once
    Wrong Item PolicyCount MistakeIgnore / Count Mistake (keep waiting) / Fail Task

    Two queries and two choices is the whole task. The rest sits behind the Advanced arrow, and most drills never open it:

    AdvancedDefaultMeaning
    Rejected ItemsemptySubtracts from an open-ended accepted family: accept Item.Extinguisher, reject Item.Extinguisher.CO2, and the rule still holds when a new variant is added. Empty is the normal case
    Require SettledonWait until the item is put down, not merely overlapping. Leave it on and let the zone’s Settle Mode decide how patient to be
    Report Each Wrong Item OnceonDo not re-report the same item every time it settles again
    Placed Item Blackboard KeynoneStores the last accepted item

    Bind On Wrong Item Placed — it passes the actor and the match quality, so “right idea, wrong agent” and “that is a wrench” can say different things. Taking a wrong item back out lets it be reported again.

    Rejected Items is rarely the answer 1.1.4

    Grading comes from the tags. The CO2 unit already scores Related against Item.Extinguisher.Foam because they share two leading nodes, so the “close, that is the CO2 unit” branch works with Rejected Items completely empty.

    The field only vetoes an accept — it cannot promote anything, so listing an unrelated object there does not make it a near miss. Reach for it when you accept a whole tag family and need to carve one item out of it.

    Needs a real zone

    The Zone query must resolve to an ASimFlowZone. An arbitrary trigger volume will not do; the task fails and logs a warning naming the query it could not resolve.

    Ordered Sequence 1.1.2

    “Press these three buttons, in this order.” Every candidate broadcasts the same tag with itself as the payload and knows nothing about the procedure; this task holds the order. Acting out of turn is a first-class outcome rather than something you notice by accident.

    PropertyDefaultMeaning
    Event TagnoneWhat every candidate raises, e.g. SimFlow.Event.ButtonPressed
    Match Child TagsonAs Wait For Event
    StepsemptyThe expected order. Each step has a Target query and Instruction text
    Out Of Order PolicyCount MistakeIgnore / Count Mistake (stay on step) / Restart Sequence / Fail Task
    Unlisted Input Is MistakeoffTreat props that are not part of the sequence as errors too
    Step Blackboard KeynonePublishes the current step index for a progress widget

    Doing step 4 when step 2 was expected is recorded at Related severity — it is part of the procedure, just early. An unrelated prop is No Match, and is ignored entirely unless Unlisted Input Is Mistake is on. Get Current Step Instruction feeds your tutorial panel.

    Recognising objects

    Flows need to name things in the level — that button, a foam extinguisher. Before 1.1.2 there was nowhere to put that, so the check ended up hardcoded in Blueprint.

    The rule

    Blueprint reports neutral facts; the flow asset decides whether they were correct. A button broadcasts that it was pressed and sends itself as the payload — it never learns which exercise is running. Change which button is right by editing one field in the flow asset. The same room then serves a dozen scenarios, and nothing rots when you author the second one.

    The identity component

    Add SimFlow Identity to the item Blueprint — not to each level instance — and set its tags. Every placed and spawned copy carries them.

    How wrong was it?

    Because tags nest, one field gives three levels of strictness — Item.Extinguisher accepts either extinguisher, Item.Extinguisher.Foam only one. More usefully, a failed match is still graded:

    Player usedvs. Item.Extinguisher.FoamFeedback you can give
    Item.Extinguisher.FoamExactcorrect
    Item.Extinguisher.CO2Related“Right idea — wrong agent for this fire class.”
    Item.Tool.WrenchNo Match“That isn't a fire extinguisher.”

    Min Related Tag Depth (default 2) sets how many leading tag nodes two tags must share to count as a near miss. A boolean match cannot express this, which is why the whole layer is built on tags.

    Streamed levels

    Specific Actor is a soft pointer resolved without a synchronous load. An actor in an unloaded World Partition cell or streaming sublevel will not resolve — use identity tags or a blackboard key for streamed content.

    Zones

    Drop an ASimFlowZone, size the box, and give its identity component a tag like Zone.PartsBin. It reports what is inside without judging it. It carries the same identity component as items rather than its own tagging scheme — one mechanism for everything a flow can name.

    A trainee holding an item over the bin has not put it down, so overlapping and placed are different events:

    DelegateFires when
    On Actor Enteredoverlap begins; may still be in the trainee's hand
    On Actor Settlednot held, and at rest for as long as Settle Mode asks
    On Actor Exitedoverlap ends

    Pick the item back up and its settle timer restarts.

    How patient the zone is about that is one field, Settle Mode 1.1.4:

    Settle ModeMeans
    InstantPlaced the moment it is inside and out of the trainee’s hands. For sockets, snap points and buttons, where the item arrives already positioned
    StandardA 0.35 s pause, and physics objects must drop below 20 speed. Suits anything put down by hand
    CustomReveals Settle Time, Settle Speed Threshold and Require Detached. For heavy props that jitter on uneven collision

    Switching away from Custom resets those three to the chosen mode’s values, so the numbers you see under Custom are always the numbers the zone is really using. Track Filter, Require Identity Component and Broadcast Flow Events sit behind the Advanced arrow; the last of those additionally raises SimFlow.Event.Placed / .Removed with the actor as payload, so a plain Wait For Event task can use a zone too.

    Tell the zone when an item is held 1.1.3

    On grab, call SimFlow Identity → Set Held (true); on release, false. Two nodes, and placement becomes exact.

    Without them a zone can only infer release from GetAttachParentActor(), which is wrong for any grab system that holds objects with a physics constraint rather than reparenting them. VRExpansion is one: of its twelve EGripCollisionType values only AttachmentGrip uses native attachment, so a gripped item looks detached from outside and a trainee can hold it steady over the zone and pass the step without letting go.

    The other thing to check: a zone only sees items whose collision responds to OverlapAllDynamic. An item set to NoCollision is invisible to it however correct its tags are.

    Mistakes and debrief

    Multiplayer

    Off by default. The server runs everything; clients mirror. Your existing Blueprint calls work unchanged — they detect they are on a client and forward to the server.

    1. Put the component on a replicated actor — Game State for a shared scenario, Player State for one flow per trainee
    2. Tick Replicate Flow
    3. Add a SimFlow Player Component to your PlayerController Blueprint
    Step 3 is the non-obvious one

    A flow on the Game State has no owning connection, so a client cannot RPC it directly. The player component sits on the PlayerController — which always has one — and relays requests. Without it, clients can watch but not act, and you get a warning in the log.

    Client-safe calls (they forward themselves): Start/Stop/Restart, Pause/Resume/Toggle Pause, Retry/Skip/Fail Current Task, Send Event, Submit Quiz Answer, Broadcast Flow Event, Request Flow Control.

    Save and load are server-only. On a client they log a warning and do nothing. Get Current Task() on a client returns the authored template task — its text is right, its runtime counters are not; read those from Get Net State.

    Object model

    USimFlowAsset                 the authored template
  └─ TArray<USimFlowNode*>    outered to the asset, survives cooking
       ├─ USimFlowTask        Instanced sub-object on Task nodes
       └─ USimFlowCondition   Instanced sub-object where used

USimFlowComponent             on an actor
  └─ USimFlowInstance         a running copy
       ├─ duplicated nodes    DuplicateObject of every template node
       └─ USimFlowBlackboard

    The template/instance split is the central design decision. USimFlowAsset is never mutated at runtime; BuildRuntimeNodes duplicates every node so each run owns its timers, retry counts and loop counters. Two actors can run the same asset, and Sub Flow nests instances (with an optional parent-child blackboard copy both ways).

    Node identity is FGuid NodeGuid, preserved across duplication. Links, save data and replication all address nodes by Guid rather than pointer.

    Execution model

    Execution is queue driven, not recursive. TriggerNodeOutput enqueues targets rather than calling into them; ProcessPendingActivations drains the queue under a re-entrancy guard.

    void USimFlowInstance::ProcessPendingActivations()
{
    if (bProcessingActivations) return;      // re-entrancy guard
    bProcessingActivations = true;

    while (PendingActivations.Num() > 0 && RunState == ESimFlowRunState::Running)
    {
        if (++Processed > MaxActivationsPerProcess) { bOverflowed = true; break; }
        const FPendingActivation Next = PendingActivations[0];
        PendingActivations.RemoveAt(0, 1, EAllowShrinking::No);
        if (USimFlowNode* Node = FindRuntimeNode(Next.NodeGuid))
            ActivateNode(Node, Next.InputPin);
    }

    bProcessingActivations = false;
    if (bOverflowed) { /* log, fail the flow */ }
}
    • A chain of a thousand instant nodes costs one stack frame, not a thousand
    • A runaway loop is caught at MaxActivationsPerProcess = 10,000 activations per step and fails the flow with an error rather than hanging the editor
    • Ordering stays breadth-first within a step

    ActivateNode refuses to re-enter an already-active node unless it overrides AllowsReentrantActivation(). Join and Loop do; nothing else does.

    Dead ends: if a node deactivates with no links and nothing else is active or queued, the instance completes the flow. That is what lets an unwired Completed pin end a simple flow cleanly.

    Pins and links

    USTRUCT() struct FSimFlowPinLink   { FGuid NodeGuid; FName PinName; };
USTRUCT() struct FSimFlowOutputPin { FName PinName; FString DisplayName;
                                     TArray<FSimFlowPinLink> Links; };
USTRUCT() struct FSimFlowInputPin  { FName PinName; FString DisplayName; };

    Nodes store their own pins and outgoing links. The editor graph is a view — on every change, USimFlowGraph::CompileToAsset clears all links and rebuilds them from the visual connections. The runtime never reads the UEdGraph.

    Well-known names live in namespace SimFlowPins: In, Out, Completed, Failed, Skipped, TimedOut, Default, LoopBody. Use them rather than string literals. (Loop's Continue pin is USimFlowNode_Loop::ContinuePin.)

    Rebuilding pins

    RebuildPins() is non-virtual and follows a template method pattern: stash existing links, clear the arrays, call the virtual BuildPins(), restore links onto any pin whose name still exists. Override BuildPins(), never RebuildPins().

    void USimFlowNode_Task::BuildPins()
{
    AddInputPin(SimFlowPins::In);
    AddOutputPin(SimFlowPins::Completed);
    AddOutputPin(SimFlowPins::Failed);
    AddOutputPin(SimFlowPins::Skipped);
    AddOutputPin(SimFlowPins::TimedOut);
}

    Because links are preserved by name, changing a Branch's case count keeps the wires on cases that still exist.

    Menu labels come from the CDO

    GetNodeCategory() places the node in the right-click menu, and the label is the class default object's GetNodeTitle(). That is why the Finish node lists as "Complete Flow".

    Task lifecycle

    USimFlowNode_Task owns a USimFlowTask as an Instanced sub-object and drives it. C++ overrides are NativeTaskStart/Tick/Pause/Resume/End; Blueprint gets ReceiveTaskStart and friends. Both fire — native first.

    ExecuteInput      → InitializeTask → StartTask → NativeTaskStart, ReceiveTaskStart
TickNode          → TickTask → NativeTaskTick, ReceiveTaskTick
                  → abort condition checked
                  → time limit checked
FinishTask(Result)→ score applied → NativeTaskEnd, ReceiveTaskEnd
                  → OnTaskFinished broadcast
                  → OwningNode->HandleTaskFinished(Result)

    HandleTaskFinished applies auto-retry if configured, then maps the result to a pin. With bFallbackToCompleted, an unwired Failed/Skipped/TimedOut pin falls through to Completed.

    FinishTask is guarded by bFinishRequested, so calling it twice in one activation is harmless. Runtime read-only fields on the task: bIsRunning, bIsPaused, ElapsedTime, RetryCount, FlowInstance, OwningNode.

    Custom tasks and conditions

    UCLASS(DisplayName = "Hold Trigger")
class MYGAME_API USimFlowTask_HoldTrigger : public USimFlowTask
{
    GENERATED_BODY()
public:
    UPROPERTY(EditAnywhere, Category = "Hold")
    float RequiredSeconds = 2.f;

    virtual void NativeTaskStart() override { Held = 0.f; }

    virtual void NativeTaskTick(float DeltaTime) override
    {
        Held = IsTriggerHeld() ? Held + DeltaTime : 0.f;
        if (Held >= RequiredSeconds) FinishTask(ESimFlowResult::Succeeded);
    }

    virtual void NativeTaskEnd(ESimFlowResult Result) override { /* unbind */ }

private:
    float Held = 0.f;
};

    Conditions override NativeEvaluate(USimFlowInstance*) const. Evaluate is non-const, applies bInvert, and lets a Blueprint ReceiveEvaluate override the native result. Override GetConditionDescription_Implementation() for the label shown on graph nodes and in the HUD.

    Blackboard and FSimFlowValue

    FSimFlowValue is a tagged union over Bool / Int / Float / String / Name / Vector / Object, kept as a plain USTRUCT so it survives SaveGame serialisation and replicates without a custom NetSerialize.

    FSimFlowValue::MakeFloat(12.5f);
Value.AsNumber();   // best-effort numeric (bool -> 0/1, string -> Atof)
Value.AsBool();
Value.AsString();
Value.Compare(ESimFlowCompareOp::GreaterOrEqual, Other);
Value.Add(Other);                // numbers, strings, vectors
Value.StripObjectReferences();   // before saving

    USimFlowBlackboard::ToEntries(bStrip) flattens the map to TArray<FSimFlowBlackboardEntry> for saving and replication, dropping object values. FromEntries restores; MergeFrom is what Sub Flow uses to copy a blackboard in and out.

    Typed accessors (GetFloat, SetVector, …) and score helpers (AddScore, GetScore) are all Blueprint-exposed. OnValueChanged(Key, NewValue) fires on every write — the component listens to it to mark the replicated blackboard dirty.

    Object references are deliberately not persisted — a raw pointer has no meaning across a save or a network boundary.

    Replication

    Off unless bReplicateFlow. Server-authoritative with client mirroring.

    UPROPERTY(ReplicatedUsing = OnRep_NetState)
FSimFlowNetState NetState;

    FSimFlowNetState carries run state, active node Guids, an FSimFlowNetTask per active task (Guid, start server time, time limit, retry count), progress, elapsed time and bHasEverStarted. Nodes, tasks and conditions never replicate. Clients already have the flow asset, so they resolve a Guid back to the authored node and read display names, instructions and quiz content locally. Bandwidth is flat with respect to graph size.

    Authority gating

    bool HasFlowAuthority() const
{
    if (!bReplicateFlow) return true;              // single player: everyone
    const AActor* Owner = GetOwner();
    return !Owner || Owner->HasAuthority();
}

    TickComponent early-outs on a mirror. Control functions check IsClientMirror() and forward to the server through the local USimFlowPlayerComponent.

    Presentation events go out as NetMulticast, Reliable RPCs carrying a node Guid. ShouldMulticastEvents() decides between multicasting and firing locally, so standalone and dedicated-server paths both fire each delegate exactly once.

    Client → server control. A flow on the Game State has no owning connection, so USimFlowPlayerComponent lives on the PlayerController and relays requests (ServerRequestControl / ServerRequestQuizAnswer / ServerRequestEvent), resolving the target by Flow Save Id. Every request passes IsRequestAuthorised(TargetFlow, Request) server-side — a BlueprintNativeEvent you override for instructor-only controls. bRestrictToOwnedFlows is the built-in default gate.

USimFlowGraphNode::RuntimeNode is marked Instanced so copy/paste duplicates it; PrepareForCopying temporarily re-parents it onto the graph node for export and PostCopyNode puts it back. PostPasteNode re-outers to the asset, assigns a fresh Guid and clears the pasted links.

    CompileToAsset runs on every graph change, on save, and on details-panel edits, rewriting positions, comments and all pin links from the visual state.

    Node property changes call RebuildPins() and broadcast OnPinsChanged, which the graph node listens to and re-syncs its Slate pins from, preserving connections by name.

    Engine compatibility

    Targets 5.6, and builds on 5.4/5.5. One line needs to match the engine. FEdGraphSchemaAction::PerformAction's location parameter has moved between FVector2D and the FVector2f-backed UE::Slate::FDeprecateVector2DParameter, and it cannot be inferred from the version number. SimFlowEditorCompat.h deduces the type from the base class declaration rather than hardcoding it.

    // SimFlowEditorCompat.h
#define SIMFLOW_PERFORMACTION_LOCATION_MODE 0
//  0  const FVector2D                                 (verified on UE 5.6)
//  1  const UE::Slate::FDeprecateVector2DParameter&
//  2  const UE::Slate::FDeprecateVector2DParameter

    A wrong setting fails loudly: "method with override specifier 'override' did not override any base class methods". Check Engine/Source/Runtime/Engine/Classes/EdGraph/EdGraphSchema.h, find the PerformAction overload taking a single UEdGraphPin* FromPin, and match its third parameter.

    Logging and diagnostics

    LogSimFlow (runtime) and LogSimFlowEditor (editor). Module startup logs at Display so it shows without changing verbosity.

    USimFlowAsset::ValidateFlow(OutErrors, OutWarnings) is public and Blueprint-callable — reachable from commandlets and automation, not just the editor panel. It reports missing Start nodes, dangling links, task nodes with no task, unreachable nodes and nodes with no outgoing connections.

    Known limitations

    LimitationDetail
    Join Wait For Any leaves the loser runningThe node stays alive to swallow the late arrival so downstream cannot fire twice, but the losing branch's task continues until the flow ends
    Blackboard replication resends the whole arrayFine for tens of keys at tutorial pacing; move to a FastArraySerializer beyond that
    Presentation multicasts are reliableAppropriate for a flow that changes task every few seconds, not for high-frequency events
    Object values are neither saved nor replicatedBy design; resolve actors at runtime
    Custom nodes require C++Tasks and conditions do not
    Tasks cannot reference level actorsThey live in the asset. Resolve by tag, pass through the blackboard, or invert to a delegate listener
    A task with no time limit and no other exit hangs silentlyNo error, no log line. ValidateFlow does not catch it — it is a runtime condition, not a graph-structure one
    An unconfigured Wait For Event succeeds immediatelyIt logs a warning, but a silent success is arguably the wrong default
